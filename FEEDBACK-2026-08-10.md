## Owner's rulings, 2026-08-10 — taken after the surveys, binding

### R1 — Map web is LIVE MapTiler, and the delivered HTML carries the key

**This overturns `map-web-discipline.md:357-381`**, which rejected live tiles in writing because they
break self-containment and ship a MapTiler key inside the delivered file. The `ZOOM_SCALE = 1.4`
control over a baked plate is what shipped instead — and it is the out-of-map button B6.14 asks to
remove.

The owner was shown the cost explicitly: the key becomes visible to anyone who opens the article, on
an account billed by usage, and the file stops working without network or an active account. His
ruling, verbatim: *"la carte doit rester interactive tout le temps sinon il n'y a pas d'intérêt
d'être sur le web si on peut pas naviguer dedans. On a le droit d'utiliser pleinement MapTiler. Et
garder l'export du HTML pas grave pour la clé."*

The reasoning is editorial and it is right: **a web map you cannot move through is a picture.** If a
beat pays the cost of being web, it should give what web gives.

So: **map × web uses live MapTiler tiles with its native zoom and pan**, constrained to the
subject's area. The baked plate remains what static and video use. The standalone HTML export
carries the key — accepted, not overlooked. `map-web-discipline.md` must be rewritten to record the
reversal and its cost rather than quietly deleting the old argument.

### R1b — The key never enters the repository, and the delivered one is domain-restricted

R1 put the MapTiler key in the delivered HTML, knowingly. It did **not** cover a second place the
key would land, which the W5/W6 spec surfaced and the owner then ruled on: **the proof beats commit
their HTML**, so a real key would enter git — and the FJM deliverable is an **MIT open-source
release**. A key on a public GitHub repository is scanned by bots within minutes of the push, and
git history keeps it after any later removal.

That matters because MapTiler **invalidates ALL of an account's keys at 100% of its spending
limit** (documented). One abused key blanks the maps in articles that are already published.

So, ruled 2026-08-10:

- **Committed artifacts carry a placeholder**, never a key.
- **`deliver` substitutes the real key** at the moment the file goes to the newsroom.
- **A guard asserts no tracked file contains a real key** — it reddens before the mistake is
  committed, not after.
- **The delivered key is a SECOND, domain-restricted key**, not the development one. MapTiler's own
  documented mitigation: copied elsewhere, it does not work. One nuance to carry into the spec — an
  account's **default key cannot be restricted**, so a dedicated one has to be created.

R1 is unchanged: the map stays live, the key stays in the newsroom's export. This only keeps it out
of the public repository.

**Audit note, 2026-08-10 — R1b landed in full; R1 landed in the seed only.** The placeholder,
`deliver`'s `substituteKeys` (reading `MAPTILER_DELIVERY_KEY` before `MAPTILER_KEY`) and
`no-key-in-the-repository.test.ts` — which asserts over **tracked** files, since an untracked scratch
file with a key is not a leak — all shipped (`68b9bcf5`, `dcc71f79`), and `configure.mjs` now accepts
the second key. R1 itself reaches no delivered beat: see B5.3.

**Closed 2026-08-10 (`10d390ad`) — clause 4 became a mechanism, and the guard's three holes are
red.** The audit corrected the note above: clause 4 was *advice*, because `substituteKeys` read
`MAPTILER_DELIVERY_KEY || MAPTILER_KEY` and this tree's `.env` holds only the second, so **every
delivery substituted the unrestricted development key**. `substituteKeys` now has three states and
no fourth — the delivery key is substituted; with neither key set the placeholder travels through
and the page ships its complete fallback layer; **with only `MAPTILER_KEY` set it throws**, naming
both ways forward (mutation: restoring the `||` reddens `should REFUSE to deliver the development

### R9.1 — what the line actually did, and which hypothesis it was

**Reproduced first, changed nothing until it was characterised.** Measured over the DRAWN pixels of
the keyed live page, the accent river was **6 px at 1600 × 900, 5 px at 1280 × 800 and 1 px at
375 × 812** — 10 206 accent pixels of blobby pipe on a desktop, whose tight meanders fused into
lumps and which was wider than the country borders it crosses, against **201 accent pixels** of
hairline scratch on a phone. The white halo that is meant to lift it off the basemap had all but
vanished at 375 px.

**Hypothesis 1 was right: a stroke that does not survive a transformed ancestor**, the second
instance of the mixed-media beat's 0.09 px park outline. The markup was blameless —
`stroke-width="3.5"` plus `vector-effect="non-scaling-stroke"`, with a comment beside the territory
outline stating that the stroke was therefore in screen pixels. It is not: `non-scaling-stroke`
neutralises the transform between the element and its nearest SVG **viewport**, which for a
`viewBox="0 0 900 420"` at `width=900 height=420` is the identity, and it does nothing about the
**CSS `transform: scale()` on the ancestor camera `<div>`**. The drawn width tracked the contain fit
exactly: 3.5 × 1.7778 = 6.22, 3.5 × 1.4222 = 4.98, 3.5 × 0.4167 = 1.46. The same arithmetic drew the
1.4 territory outline at 0.58 px on a phone — precisely what that comment claimed it had fixed.

**Hypotheses 2 and 3 were tested and cleared, by measurement, not by argument.** The fit is uniform
(the screen CTM's `a` equals its `d` at every width), so nothing is drawn in a non-square space. And
the overlay is exactly registered against the live camera: over 13 sampled route points at each of
the three widths, the SVG's screen position and `map.project()` of the same place differ by **0 px
in x and 0.25 px in y** (the container's own half-pixel), with asked zoom equal to delivered zoom to
four decimals — 5.569 / 5.247 / 3.476, `renderWorldCopies: true`, no clamp. The plate-frame trap was
a real candidate and it is not what happened here.

**The fix**: `STROKE_SCREEN_PX` (route 3.5, halo 7, territory 1.4) and `strokeWidthsFor(camera)` in
`route-drive.mjs` — one derivation dividing the fit back out, called by `MapFrame.tsx` for the SSR'd
no-JavaScript picture and by `initRouteScrolly` on every paint, written beside the transform that
made it necessary. Leader lines untouched: they live outside the camera box and were always in frame
pixels. **After, on the keyed page: 3.69 / 3.72 / 3.99 px** — a 0.30 px spread across a 4.3× range
of camera scale, where it had been 4.81 px.

**The guard is on the paint, and it is `drive.mjs` that takes it** (`scroll-report.mjs`'s
`lineWeight`): the line's own thickness, integrated as accent coverage across perpendiculars sampled
along its geometry — sub-pixel, because 1 px and 1.5 px are the same integer — must sit in [2, 5] px
at every driven width AND agree across widths to within 1.5 px. **The second clause is the one that
names the defect class**; a stroke tracking the camera cannot pass it even where one width happens
to land inside the band. M11 in `scroll.test.ts` carries the mutation and the red it produced, run
in a copy under `/tmp`: the pure half fails on the arithmetic, and the re-rendered, re-driven page
fails with *"the river draws 1.80px at one width and 6.61px at another (spread 4.81px, allowed
1.5px) — the stroke is tracking the camera's scale instead of the screen."* **Under that mutation
every other guard in the beat, and all six scroll sweeps, stay green** — as would any assertion on
the markup, which says `3.5` throughout.

**The class, for whoever meets it next:** anything inside a CSS-transformed camera box scales with
the camera, and no SVG attribute exempts it. This beat had already learned it once for TEXT (the
badges are fixed-size HTML because a 12 px numeral drew at 5 px) and the strokes kept the defect
because an attribute was believed instead of measured. The same shape is worth looking for wherever
a beat draws vectors over a live map through a transformed box.

### R9.3 — the two fragments: the dash is not it, and the invariant is now held on the paint

The obvious suspect is a repeating dash. A progressive reveal declares a dash as long as the path
and animates the offset, and `stroke-dasharray` **repeats infinitely** — a single value means "dash
L, gap L, dash L…" — so the tail of the previous repetition can reappear at the far end. That is
exactly a head fragment, a hole, and a tail fragment. **It is not what this build does**, and the
arithmetic says why: with offset `h` in [0, L] the dash covers [-h, L-h] and the next one begins at
2L-h, which is ≥ L, so exactly one dash intersects the path. The related concern — that the stored
length went stale when the stroke scaling changed — was checked rather than assumed: the declared L
(1272.04) agrees with the rendered `getTotalLength()` (1272.0430908203125) to **0.0031 user units**,
and `getTotalLength` is in USER space, so a CSS transform on an ancestor cannot affect it.

**Looked for, before changing anything**: 1508 driven frames at **375, 1280, 1512, 1600, 2560 and
3440 px**, both directions, no settle wait — every frame one painted run starting at the source and

### R9.5 — the card is an overlay, and it enters no measurement of the visual

pieces at 1600 × 900, three at 1280 × 800, and hidden whole on the phone. Every number was correct

**The rule is written at the vehicle's level, not this beat's**, because it decides every scrolly:
the **tenth correction** in `scrolly/references/scrolly-discipline.md`, with the reason, so that
nobody builds a second occlusion-aware guard in six months. *A visual's own state, and every
assertion made about it, are independent of the prose layer travelling over it.* The practical test
it gives a new guard: would the same visual, rendered with the prose layer deleted, produce a
different verdict? Then it is measuring the overlay.

**What survives is the instrument/subject distinction, which is the useful half.** This probe reads
composited pixels, so it must still know where the card is — otherwise the card's white fill reads as
missing river and the guard invents a hole every time it crosses the line. A pixel behind the card is
now **unobservable**: it supports no claim in either direction, it is recorded as a confidence figure

Read as a whole rather than as 40 items, three things dominate, and they are not beat defects:

1. **Furniture, palette and typeface are not yet the newsroom's.** B1.1–B1.3 repeat on every one of
   the 23 types because they are properties of the CRAFT SKILLS, not of any beat. The palette

   **A note on the word, because it decides the architecture.** An earlier draft of this paragraph
   said "engines". That is the ORIGINAL Splash's shape (`skills/` at the repository root), and
   reaching for it here would propose exactly what this branch refuses. The twin is Tom Vaillant's
   self-contained-skill method: *a skill must stay copy-pasteable on its own, so helpers are
   duplicated rather than imported* — enforced by `no-cross-skill-imports.test.ts`. So the answer to
   "make this true for 23 types" is never "extract a shared layer"; it is **the same change, made
   identically in each craft skill, with a walking parity test proving the copies stay in step**.
   `render-still-parity.test.ts` and `video-helper-parity.test.ts` walk the tree rather than taking

2. **Size is not yet a dimension of production.** B2.1 and B3.2 are the same missing idea from two

3. **Maps are built for one camera.** B4.1 is the largest single piece of work in this file: every
   map beat is tuned to its own extent, and the tool has to hold a city and a planet with the same
