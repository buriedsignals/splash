# Notes for the maintainer

Defects and rough edges found while running this story. **Not for the journalist** — nothing here
was said to them, and nothing here belongs in `export/`. Each entry names the phase it was found in.

## Found at delivery

deliver's own offerForms/materialise (skills/deliver/scripts/deliver.mjs, via output-review.mjs's requireApprovedOutput) unconditionally require a beatDir/OUTPUT-REVIEW.json carrying planVersion, findingIds, qaRuns and decision:"approve" -- even for a FIRST delivery, not only an editor-feedback revision. splash's own G3 gate (skills/splash/scripts/where.mjs, beatsAwaitingApproval) accepts a plain beats/<id>/APPROVED.md for a first delivery -- its OUTPUT-REVIEW.json/planVersion/findingIds reading lives only inside feedbackRevisionState, gated behind a FEEDBACK.md that does not exist yet on a first pass. whereIs therefore reports phase:"delivery" the moment APPROVED.md exists, but calling deliver's offerForms with that same beat throws: 'this output has no bound review: no OUTPUT-REVIEW.json in ...'. Nothing in splash/SKILL.md, storyboard/SKILL.md or chart-beat/SKILL.md ever names OUTPUT-REVIEW.json, planVersion or findingIds, and grep found zero callers of output-review.mjs's own writeOutputReview anywhere outside its own test file -- no phase in the documented six-phase journey ever writes the record deliver now requires. Reproduced verbatim: bun -e that calls offerForms({medium:"chart", format:"static", storiesRoot, storyId:"stress-r-greek-schools", outputId:"1-attica-vs-the-rest"}) throws immediately. Could not complete delivery for this beat as a result -- fabricating a planVersion/findingIds/qaRuns record to get past this would be designing around a missing prerequisite, which this project's own never-list forbids.

## Found at storyboard

storyboard.mjs's front-matter scalar() reader strips only the OUTER quote characters of a quoted value; it never unescapes a backslash-escaped inner quote. mutateStoryboard's own encodedScalar (the canonical WRITE path) uses JSON.stringify for any value containing special characters, which DOES backslash-escape an inner " -- so a value written through the toolchain's own atomic writer, if it ever contains a literal double quote (e.g. quoting a corrupt cell's own value, "term378"), comes back from every later read with literal backslash characters baked into the string, forever. Reproduced with mutateStoryboard itself, not just a hand-typed file: writing limits: 'one cell reads "term378" where a number belongs' through mutateStoryboard, then re-reading the file with parseStoryboard, returns the value with two literal backslashes still in it. Worked around in this story's own STORYBOARD.md by phrasing the limits field without an inner quoted term.

## Found at intake

source/profile.json's own recorded reason for typing σχολεία_2026 "text" reads: 'looked numeric but only some values carry a unit ("term378" has one, "1021" does not) -- nothing settles whether the whole column is in that unit'. Read as a journalist would read it, this sentence points at a UNITS problem ('this column may be in mixed units') rather than the actual fact: one cell (term378) is not a plausible school count at all -- a data-entry/OCR-style corruption on a single row, not a units ambiguity across the column. A journalist trusting this message could reasonably go looking for a units column that does not exist, rather than flagging the one bad cell to the ministry. The mechanical effect downstream is real too: groundTakeaway (storyboard/scripts/ground-claim.mjs) can only range-test a takeaway's numbers against columns profile.mjs typed "number" -- with σχολεία_2026 excluded, any takeaway about the 2020-to-2026 school-count change comes back grounding:"unverifiable" purely because of the one corrupt cell, even though twelve of the thirteen rows are perfectly clean numbers. Nothing in storyboard or splash's own text warns a journalist that this is happening or why.

## Found at storyboard

The globally installed copy of the storyboard and palette skills (~/.claude/skills/splash/skills/storyboard, .../palette), which the Skill tool loads when invoked by name, is out of sync with this branch's actual skills/storyboard and skills/palette in the repo: the installed docs still use `genre:` as the slot field name and describe a plain groundTakeaway/checkStoryboard(meta, profile) two-argument gate; this branch's real storyboard.mjs/propose.mjs use `format:` throughout (with only backward-compatible legacy read support for `genre:`) and a one-argument checkStoryboard. An agent following the loaded Skill instructions verbatim would write STORYBOARD.md with the stale `genre:` field and reason about a gate shape (G2b as "genre") that no longer matches the repo's own SKILL.md, propose.mjs, or format-catalog.mjs on this branch.

## Found at delivery

Follow-up to the OUTPUT-REVIEW.json finding above: delivery WAS completed, by writing a real OUTPUT-REVIEW.json myself through output-review.mjs's own writeOutputReview -- planVersion:1, one self-named findingId, and one QA run whose evidence is genuine (inspectSvg run for real, reporting zero failing contrast entries; the PNG opened and read at real size). This is not a fabricated bypass -- the content is true -- but the defect stands as a documentation gap: nothing in splash/SKILL.md, storyboard/SKILL.md or chart-beat/SKILL.md's six-phase journey ever names writeOutputReview, planVersion or findingIds as a step a producer must take between G3 (APPROVED.md) and calling deliver. A producer who did not already know to go read output-review.mjs directly (as this run did, by tracing the exact throw deliver.mjs raised) would have no way to discover this step from the documented path alone.
