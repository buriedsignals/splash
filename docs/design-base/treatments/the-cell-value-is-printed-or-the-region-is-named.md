## The rule, which has two answers and states its own condition

Colour cannot be read back to a number. A grid has to repair that, and the corpus shows two repairs
whose condition is simply how many cells there are.

## Answer one — print the number in every cell

`100.datavizproject.com`'s viz49 has **six** cells and prints the value in all six, centred, in
white. That record's reason, verbatim: *"a heatmap's known weakness is that colour cannot be read
back to a number; printing the number in the cell repairs it, and at this cell count there is room."*

The same archive does it twice more from the other direction — viz100 puts a bar under the number in
a table cell, viz35 prints the value large and lets the arc be a texture, conceding outright that
*"the data visualization is kind of secondary"*. At six cells that is an honest configuration.

## Answer two — name the region

Information is Beautiful's pin-code poster has **ten thousand** cells and prints none. It draws
dashed rectangles around blocks and names what the block means: `Those using their birth date in
DD/MM or MM/DD formats`, `using same two pairs of numbers`. That record carries the rule the fork
rests on: *"the finding in a heatmap is almost always a **shape**, and a callout on one cell cannot
say it."*

The same poster still calls out individual cells where the cell itself is the story — `7410`,
`4321`, `2580`, `1234` — so the two scales of annotation coexist; the region is the default and the
cell is the exception.

## What is not admissible

A grid that does neither, and leaves the reader to invert a colour by eye.

## How a beat chooses

By measurement, not by taste: the value register's own band against the cell the layout actually
gives. If the number fits, print it. If it does not, the beat names its blocks instead — and says on
the plate that it is doing so, because a reader cannot tell a grid that chose not to print from one
that forgot.
