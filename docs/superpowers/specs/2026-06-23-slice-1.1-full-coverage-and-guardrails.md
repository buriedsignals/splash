# Slice 1.1 — Full chart-type coverage + best-practice guardrails

> Extends the proven `dw-chart` slice. Two parallel workstreams: (A) cover every Datawrapper **chart** type,
> (B) wire the KB best-practices into the code as **enforced guardrails** (not just docs ② is meant to follow).
> Maps (3 DW types) are out of scope — they go to a future map skill. No tiers.

## Why

The slice proved the loop on 9 chart types with machine-checkable conformance applied. Verification (driving
the real ②→dw-chart loop) showed the gaps: only a subset of types, several best-practices live only in the
KB docs (data-to-viz caveats, sorting, colour ceiling) and are not enforced, and annotations aren't supported.
This closes both.

## Workstream A — Full type coverage

### A1. Expand the type list
`CHART_TYPES` becomes the 24 in-scope ids. The producer is already generic (create→data→patch→publish→export);
most types render once the type id is valid and the data shape fits.

### A2. Per-type minimal data-shape validation
`validateChartSpec` gains a per-type minimum-columns check (catch obvious mismatches early; rely on the real
DW API for the rest — real keys, real failures):

| Type family | Min data shape |
|---|---|
| single-series (column-chart, d3-bars, d3-lines, d3-area, d3-pies, d3-donuts, d3-dot-plot, election-donut-chart, waterfall, tables) | ≥1 label col + ≥1 value col |
| multi-series (grouped/stacked/split/multiple-* , multiple-lines, multiple-columns) | ≥1 label col + ≥2 value cols |
| 2-value (d3-scatter-plot, dual-axis, d3-range-plot, d3-arrow-plot, d3-bars-bullet) | ≥2 value cols (x/y, min/max, value/target) |

A `dataShape(csvText)` helper (pure) returns `{ columns: string[]; rows: number }`; the validator uses it.

### A3. Visual verification
A `scripts/produce-all-types.ts` produces one chart per in-scope type (type-appropriate sample data) via the
real loop, prints `type → publicUrl → ok/fail`. A human spot-checks a representative set of PNGs. Any type that
the DW API rejects is reported (not worked around).

## Workstream B — Best-practice guardrails (KB rules → enforced code)

Each rule below currently lives only in `knowledge/references/` (docs). This wires it into the validator,
the producer, or the spec so it is **enforced**, not hoped-for. Split into hard errors vs auto-fixes vs warnings.

### B1. Colour ceiling (hard) — design-principles "categorical max 4-8, ceiling 10"
`seriesColors` already must be all Okabe-Ito. Add: **≤8 entries** (hard error beyond). Single-series charts
(those not in the multi-series family) must not declare `seriesColors` with >2 entries (the "≤2 colours" rule
applies to single-series emphasis). Multi-series families are exempt up to the ceiling.

### B2. Part-to-whole slice cap (hard) — data-to-viz caveat
For `d3-pies`, `d3-donuts`, `election-donut-chart`: if the data has **>5 slices**, reject with
`pie/donut with N slices — group into 'Other' or use bars (data-to-viz caveat)`. (FT/data-to-viz: pie only with
few slices and clear differences.)

### B3. Ranking sort (auto-fix) — design-principles "sort categorical data before plotting, always"
`ChartSpec` gains `sort?: 'desc' | 'asc'`. When set, the **producer sorts the CSV by the value column** before
upload (enforced in code, not left to ②'s discretion). The suggest-chart skill sets `sort: 'desc'` for
ranking-intent charts (`d3-bars`, `column-chart` used for ranking).

### B4. Annotations (feature) — design-principles "annotations explain WHY, highlight outliers/trend breaks"
`ChartSpec` gains `annotations?: { text: string; x?: string|number; y?: number }[]`. `spec-to-metadata` maps
them to DW `metadata.annotate.notes` (text annotations). A produced chart with an annotation is the proof.

### B5. Number-format default (auto-fix) — Datawrapper/ONS "strip noise, abbreviate"
If `numberFormat` is absent on a numeric chart, default it to a sane token (`'0,0.[00]'`) rather than leaving
DW's raw default. Auto-applied in `spec-to-metadata`.

### B6. Title-is-insight (warning, not hard) — ② territory, but a code smell-check
A lightweight check flags titles that are obviously not insights (e.g. equal to the data's column header, or a
bare year range like `2018-2023`). Returns a **warning** in the validator result (`{ ok, errors, warnings }`),
never blocks — judgment stays with ②, but the smell is surfaced.

### B7. Strengthen the ② skill doc
Update `suggest-chart/SKILL.md`: encode B1-B6 as instructions (set `sort` for ranking; ≤2 colours single-series
/ distinct Okabe-Ito multi-series ≤8; group pie slices >5; add an annotation for the key outlier; write the
title as an insight). So ② proposes within the guardrails the code enforces.

## Interfaces (the contract changes)

`ChartSpec` gains: `sort?: 'desc'|'asc'`, `annotations?: {text,x?,y?}[]` (seriesColors/transpose already added).
`validateChartSpec` returns `{ ok: true, spec, warnings: string[] } | { ok: false, errors: string[] }`
(adds `warnings`). New pure helpers: `dataShape(csv)`. `specToMetadata` maps annotations → `metadata.annotate`,
applies number-format default, and the producer applies `sort` to the CSV.

## Out of scope
- Maps (choropleth/symbol/locator) and video — separate skills.
- ②'s full editorial judgment (it stays an LLM step; we only enforce the machine-checkable rules + surface smells).
- Per-type pixel-perfect styling beyond the guardrails.

## Success criteria
1. `CHART_TYPES` = the 24 in-scope DW chart types; `produce-all-types.ts` produces each via the real loop with a per-type ok/fail report; failures (if any) are reported, not hidden.
2. Guardrails enforced with tests (real API where it touches DW): colour ceiling (≤8, single-series ≤2), pie/donut >5 slices rejected, ranking auto-sorted in the uploaded CSV, annotations land on the live chart (`metadata.annotate`), number-format default applied, title-smell warning surfaced.
3. `validateChartSpec` returns `warnings`; existing 20 tests still green.
4. `suggest-chart/SKILL.md` documents the guardrails so ② proposes within them.
5. No tiers anywhere; all credited; English; no Claude/Anthropic mention.
