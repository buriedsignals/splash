### R1 — Map web is LIVE MapTiler, and the delivered HTML carries the key

**This overturns `map-web-discipline.md:357-381`**, which rejected live tiles in writing because they
break self-containment and ship a MapTiler key inside the delivered file. The `ZOOM_SCALE = 1.4`
control over a baked plate is what shipped instead — and it is the out-of-map button B6.14 asks to
remove.

The owner was shown the cost explicitly: the key becomes visible to anyone who opens the article, on
an account billed by usage, and the file stops working without network or an active account. His
ruling, verbatim: *"la carte doit rester interactive tout le temps sinon il n'y a pas d'intérêt
d'être sur le web si on peut pas naviguer dedans. On a le droit d'utiliser pleinement MapTiler. Et
garder l'export du HTML pas grave pour la clé."*

The reasoning is editorial and it is right: **a web map you cannot move through is a picture.** If a
beat pays the cost of being web, it should give what web gives.

So: **map × web uses live MapTiler tiles with its native zoom and pan**, constrained to the
subject's area. The baked plate remains what static and video use. The standalone HTML export
carries the key — accepted, not overlooked. `map-web-discipline.md` must be rewritten to record the
reversal and its cost rather than quietly deleting the old argument.

### R1b — The key never enters the repository, and the delivered one is domain-restricted

R1 put the MapTiler key in the delivered HTML, knowingly. It did **not** cover a second place the
key would land, which the W5/W6 spec surfaced and the owner then ruled on: **the proof beats commit
their HTML**, so a real key would enter git — and the FJM deliverable is an **MIT open-source
release**. A key on a public GitHub repository is scanned by bots within minutes of the push, and
git history keeps it after any later removal.

That matters because MapTiler **invalidates ALL of an account's keys at 100% of its spending
limit** (documented). One abused key blanks the maps in articles that are already published.

So, ruled 2026-08-10:

- **Committed artifacts carry a placeholder**, never a key.
- **`twin-deliver` substitutes the real key** at the moment the file goes to the newsroom.
- **A guard asserts no tracked file contains a real key** — it reddens before the mistake is
  committed, not after.
- **The delivered key is a SECOND, domain-restricted key**, not the development one. MapTiler's own
  documented mitigation: copied elsewhere, it does not work. One nuance to carry into the spec — an
  account's **default key cannot be restricted**, so a dedicated one has to be created.

R1 is unchanged: the map stays live, the key stays in the newsroom's export. This only keeps it out
of the public repository.

**Audit note, 2026-08-10 — R1b landed in full; R1 landed in the seed only.** The placeholder,
`twin-deliver`'s `substituteKeys` (reading `MAPTILER_DELIVERY_KEY` before `MAPTILER_KEY`) and
`no-key-in-the-repository.test.ts` — which asserts over **tracked** files, since an untracked scratch
file with a key is not a leak — all shipped (`68b9bcf5`, `dcc71f79`), and `configure.mjs` now accepts

**Closed 2026-08-10 (`10d390ad`) — clause 4 became a mechanism, and the guard's three holes are
red.** The audit corrected the note above: clause 4 was *advice*, because `substituteKeys` read
`MAPTILER_DELIVERY_KEY || MAPTILER_KEY` and this tree's `.env` holds only the second, so **every
delivery substituted the unrestricted development key**. `substituteKeys` now has three states and
no fourth — the delivery key is substituted; with neither key set the placeholder travels through
and the page ships its complete fallback layer; **with only `MAPTILER_KEY` set it throws**, naming
both ways forward (mutation: restoring the `||` reddens `should REFUSE to deliver the development
key`). And the guard, measured green by the audit on three leaks, is red on all three plus a fourth:
a tracked 9 MB `.html` (the size skip), a tracked `leak.png` (the extension skip), a **different**
21-char key in a committed style URL, and `MAPTILER_DELIVERY_KEY`'s own value — closed by a chunked
BYTE scan with no ceiling and no extension list, by scanning for the delivery key by name, and by a
value-INDEPENDENT rule that every `api.maptiler.com/…?key=` in a tracked file is the placeholder,
"a key" matched by shape (16+ alphanumerics). That last check carries an anti-vacuity pin, because
it passes trivially in a tree with no live map in it — which is the tree the audit found.

### R7 — A map on a SCROLLY is live MapTiler too, and it has no controls

The owner drove the map scrollys and reported the fact rather than a preference: *"j'ai l'impression
que le scrolly map n'utilise pas MapTiler correctement, je ne vois aucun canvas dans le DOM. Or il
faut tout le temps utiliser MapTiler."* He was right — `maplibregl`, `api.maptiler.com` and
`<canvas>` were all **0** on all three committed map-scrolly pages. This extends R1 to the scrolly
genre: **a map uses MapTiler everywhere.**

The reasoning that kept the plate was a real argument and is preserved, marked overturned, in each
beat's own BRIEF: a scrolly's cameras are AUTHORED, a finite set a plate can hold, and a reader
mid-scrub can outrun a tile server. It is answered rather than dismissed — the cameras being known
at build time is exactly what makes them **warmable**, and the plate stays UNDERNEATH the tiles as
the fallback layer rather than instead of them.

Second half, same day: *"Pas de controls sur le scrolly, le scroll pilote et la map doit prendre
toute la largeur."* **No `NavigationControl`, no drag, no wheel, no keyboard pan** — the map is
constructed `interactive: false`. This is a deliberate DIFFERENCE from map × web, where R1 requires
the controls, and it is written into `twin-scrolly/references/scrolly-discipline.md` as a
distinction between the two genres with the reason (on a scrolly the scroll already drives the
camera, so a reader-moved camera is taken back by the next step) rather than left as an omission
somebody later "fixes".

| Page | `maplibregl` | `api.maptiler.com` | `<canvas>` in the live DOM |
|---|---|---|---|
| `mapscrolly-one-map-europe-carbon/render/one-map-four-readings.html` | 0 → **449** | 0 → **2** | 0 → **1** |
| `mapmore-scrolly-danube/render/danube-scrolly.html` | 0 → **449** | 0 → **3** | 0 → **1** |
| `mapscrolly-quakes-three-ways/render/quakes-four-maps.html` | 0 → **449** | 0 → **2** | 0 → **1** |

**The `<canvas>` count is on a KEYED copy**, and that distinction is the one that costs an hour if
nobody states it: the committed file carries the placeholder (R1b) and both live layers refuse to
boot on one, so opening a tracked page straight from the checkout shows the baked fallback and
**0 canvases** — correct, and indistinguishable from the defect. `bun scripts/open-live-copy.mjs`
writes keyed copies outside the repository and serves them over http (`file://` is an opaque origin
and MapLibre's fetches fail there silently, which looks like the same defect again).

Guarded by `splash-twin/test/map-scrollys-are-live.test.ts`, which fails BOTH ways — a scrolly that
has stopped being live, and a scrolly that has grown a control — with its three mutations recorded.

**What the warm measured**, keyed copy outside the tree, 1600×900, one localhost hop to
`api.maptiler.com`. On the beat with a MOVING camera (`one-map`, four authored cameras): 10 cameras
walked in **367–567 ms**, 24 requests; at reading speed (30px per animation frame, 126 frames)
**13 frames still had a tile outstanding, against 34 of 126 with the warm removed**; at a trackpad
flick (400px/frame, 10 frames) **0 against 1**. Settle after the gesture: 1–4 ms either way.

**And an honest negative on the fixed-camera beats.** `danube` has ONE camera: the warm costs
**17–34 ms at 1600×900, 166 ms at 375×812**, and the `--no-warm` control measures the same 0/0/0
missing frames. That is not the warm failing — the map is constructed already pointing at its only
camera, so `load` already implies those tiles arrived and the warm adds only the stricter `idle`.
Kept because the right shape costs a third of a frame, and recorded as buying nothing measurable
rather than claimed as a saving.

**No scrub speed was found at which the tiles could not keep up** — and the honest caveat is that
this is one localhost hop to a fast network, which is exactly what the fallback plate under the
tiles is there for.

**`interactive: false` turned out to be load-bearing beyond the ruling.** A live map fills the
frame, so the reader's pointer rests on it, and an interactive MapLibre canvas swallows the wheel:
the piece would refuse to scroll where a reader is most likely to be pointing. Verified with a real
`Input.dispatchMouseEvent` wheel rather than `scrollTop =` (which bypasses hit testing): 25 ticks at
(300, 600), in the middle of the map, moved the scrollport **0 → 3000 px** and `data-progress`
**0.0000 → 2.4688** on both beats tested.

### R8 — A photograph on a scrolly is CONTAINED and fills the frame

*"Pour les scrolly images respecte le ratio mais remplis au max en largeur ou hauteur."*

`twin-scrolly`'s seed image track was `object-fit: cover`, and `scrolly-discipline.md` argued for it
in writing: a photograph is scenery, "no part of the image is a claim". That is backwards for the
thing the track carries — a journalist's photograph is a document. The seed is `contain` now, the
doctrine and `SKILL.md` move a photograph from scenery to evidence, and **the letterbox is the
render's own `ground`**, the value every piece of the page's furniture is already derived from, so
it is a colour someone chose rather than a default nobody picked.

"Fill" was the half the proof beat was missing: it contained, but into `CONTENT_TOP`, reserving 28%
of every frame for a panel that cannot park anywhere since the vehicle's ninth correction.
`PROSE_LANE` is 0 and the picture now grows until it meets the frame on whichever axis binds.

**What the centred card does to a contained portrait picture, measured**: the ninth's 409px card
covers part of the photograph on 93 of 126 frames at 1600×900 (worst 15.6% of its area), 82 of 109
at 1280×800 (21.9%) and 67 of 88 at 375×812 (28.2%), with a run of 27 consecutive frames at
1600×900 where the card's vertical edge sits INSIDE the picture. Nothing on the photograph is text,
so this is not the "broken label" the ninth's own rule forbids — it is an opaque band across the
middle of a document. Not worked around: moving the picture off-centre so a centred card misses it
would rebuild the side-by-side arrangement the owner rejected. **Reported for a ruling.**

### R2 — Export sizes: three fixed for static and video, a RANGE for web

Landscape for YouTube and article-web, portrait for stories, square for social posts. **Charts and
maps both**, one model, no per-family exception — which settles the geo rule 12 tension by making
the target aspect an input the camera takes, rather than a frame the map is cut into.

**Web is not a fourth size.** The owner: *"pour les tailles en web oui ça doit être responsive car
on intégrera ça dans le CMS donc ça fonctionnera un peu comme un composant embed."* Web fills its
container, whatever the CMS gives it. The `export-sizes` survey found the original Splash already
models exactly this (`interactiveAspect: "responsive"` on every channel row), which is evidence the
shape is right — not licence to import it.

## What this feedback is really saying

Read as a whole rather than as 40 items, three things dominate, and they are not beat defects:

1. **Furniture, palette and typeface are not yet the newsroom's.** B1.1–B1.3 repeat on every one of
   the 23 types because they are properties of the CRAFT SKILLS, not of any beat. The palette
   threading landed 2026-08-09 (`readPalette`); typeface and credit placement did not.
   *Audited 2026-08-10: credit placement has since reached the seeds (5 of 5) and 3 proof
   components; typeface still reaches no render at all. See B1.1 and B1.3.*

   **A note on the word, because it decides the architecture.** An earlier draft of this paragraph
   said "engines". That is the ORIGINAL Splash's shape (`skills/` at the repository root), and
   reaching for it here would propose exactly what this branch refuses. The twin is Tom Vaillant's
   self-contained-skill method: *a skill must stay copy-pasteable on its own, so helpers are
   duplicated rather than imported* — enforced by `no-cross-skill-imports.test.ts`. So the answer to
   "make this true for 23 types" is never "extract a shared layer"; it is **the same change, made
   identically in each craft skill, with a walking parity test proving the copies stay in step**.
   `render-still-parity.test.ts` and `video-helper-parity.test.ts` walk the tree rather than taking
   a list, which is what makes deliberate duplication safe at 20+ copies — and
   `helper-parity.test.ts`'s hand-written list is the standing counter-example: it turned the suite
   red for a correct change, and two agents kept a dead export alive to satisfy it.
2. **Size is not yet a dimension of production.** B2.1 and B3.2 are the same missing idea from two
   sides: a beat is produced at one size today. Static/video need portrait, square and landscape;
   web needs to be genuinely fluid with a mobile form.
3. **Maps are built for one camera.** B4.1 is the largest single piece of work in this file: every
   map beat is tuned to its own extent, and the tool has to hold a city and a planet with the same
   machinery.

Everything in Part A is one further thing: **the journey talks to the journalist about the wrong
subjects, in the wrong order, and sometimes about us.**
